How it works

One read-only script, over the SSH you already use.

No daemon, no exposed Docker socket, no stored password. Every 30 seconds Ballast runs a small script on the NAS and reads what it prints.

1

Your Mac connects over SSH

Ballast reuses your SSH key and ~/.ssh/config. An alias you already type in Terminal works here.

2

A read-only script inspects Docker

ballast-agent asks Docker to describe the containers. It can inspect; it cannot build, pull or delete.

3

The menu shows what came back

Each container becomes a row with a status and a port. Click it to open that service.

A crash at 3am no longer leaves no trace

Each check is compared with the last, so something that fell over and came back while you slept still shows up, with how long it was down.

Notifications that don't cry wolf

You only hear about a non-zero exit or an out-of-memory kill. Clean stops, restarts Docker already handled, and anything you did yourself stay quiet.

Works away from home

Give Ballast a second hostname — a Tailscale name works well — and it switches over when the local one stops answering.

Only the rows you care about

Hide the containers you never click, filter by name, and sort by status so problems float to the top.

Privacy & security

Nothing leaves your Mac.

One machine, over SSH, with the key already on your Mac. No cloud, no account, no telemetry. This paragraph is the whole policy.

  • No credentials in the app Key authentication and your existing ~/.ssh/config — no password is ever asked for, so none can leak.

  • No Docker socket exposed The socket stays root-only. One sudoers rule, scoped to one root-owned script that can only inspect and start, stop or restart.

  • No daemon on the NAS Nothing listens, nothing runs between checks. The script runs over SSH and exits.

  • Container names can't reach a shell A name is checked against the live container list and travels as its own argument, never inside a command string.
